# Youcai Foundation V1 backend

## Integration and contract

Mount `crmRouter` from `server/crm/api.ts` at `/api`. The router supplies JSON parsing, no-store headers, same-origin checks, CSRF checks and safe errors. It does not mount native OAuth or use the legacy starter `users` table. Every business endpoint resolves the current opaque session and recomputes current ACTIVE-role permissions from SQL. `admin`, `ceo`, `pricing`, `sales`, `employee`, `technician` are role **codes**; their reference names are the exact six requested names. Shared constants and DTOs are exported by `shared/crm.ts`. Customer and legal entity enums are their exact English specification labels. Region codes: `NA`, `CA`, `SA`, `EU`, `MENA`, `APAC`, `OTHER`.

Public routes: `GET /auth/config` returns exactly `{emailReady:boolean}`; `GET /auth/me` returns `{user:null}` or `{user,csrfToken}`; registration, login, logout, verify, resend, forgot and reset are under `/auth`. Mutation payloads use `Content-Type: application/json`; bodyless logout and contact deletion are supported. Authenticated mutations additionally require `X-CSRF-Token` from login or `/auth/me`, and include credentials. Login sets `youcai_session` with `HttpOnly; Secure; SameSite=None; Path=/`, eight-hour absolute expiry, no bearer/JWT role claims. HTTPS Preview/public origins are supported without inferring an internal HTTP scheme. A supplied Origin/Referer must match the HTTPS request Host or configured trusted APP_PUBLIC_URL origin. Mail links use the actual frontend `/verify-email?token=…` and `/reset-password?token=…` pages.

Email verification requires `POST /auth/verify` with exactly `{token,password}`. The mailbox owner must choose a password in the mailed-link form and explicitly submit it; merely opening the link or submitting a token alone cannot verify or bootstrap an account. The password uses the shared 12–128-character schema. Registration's password is provisional until ownership is confirmed, and duplicate registration retains the generic response without changing the existing account. The verification form's submitted password replaces that provisional credential, even if the mailbox was preregistered by someone else. Invalid payloads and invalid, expired, wrong-purpose, already-consumed or ineligible-account links return the same generic HTTP 400 message, without credentials or tokens in responses/logs. Successful verification does not create a session; the owner signs in with the password chosen on the verification form.

Business endpoints implement the agreed `/reference`, `/dashboard`, customer/contact CRUD and archive/restore, `/company`, `/users`, `/roles`, `/audit`, and country-region remapping contract. List customers uses a fixed page size of 25, one-based `page`, optional exact `type`, alpha-2 `country`, region code and uppercase `ACTIVE`/`ARCHIVED` status. No status filter means both statuses. Audit returns `{items,pagination:{total,page,pageSize}}`. Users returns the complete `{items}` directory using batched role/permission joins. Invalid fields return HTTP 422 `{message,errors:[{field,message}]}`; policy failures return 403 or 409. Contacts delete returns 204. Customer archive returns `{customer}`. Duplicate warnings include matching customer names and IDs and never impose uniqueness. Registered Corporation, LLC and Government Entity require legal name. Archived customers must be restored before other edits.

All active users may access reference/dashboard, but dashboard customer totals are zero when the user lacks customers.read, and pending-user counts appear only for authorized top-level users. Recent activity is limited to the user's own events unless audit.read is granted. Company, user, and role settings additionally require exact current admin/ceo membership, not merely permissions assigned to another role. User approval requires users.approve; other status/role changes require users.manage. Self role/status changes are rejected. Admin/CEO core V1 permissions cannot be removed. No role creation/deletion and no product tables, APIs, records, uploads or pricing exist.

## Database and setup

Actual managed SQL version verified: `8.0.11-TiDB-v8.5.3-serverless`. All SQL strings containing user values are parameterized mysql2 statements; only compile-time column identifiers and bounded integers appear as SQL literals. The migration is additive, uses InnoDB, UUID business identities, foreign keys and indexes, and uses no triggers or procedures. Legacy starter users remain untouched.

```sh
pnpm exec tsx scripts/migrate.ts
pnpm exec tsx scripts/seed.ts
```

Both commands finish and close the pool. Migration application is checksum-tracked in `crm_schema_migrations`; add a new migration instead of editing an applied file. DDL auto-commits, so individual statements are rerunnable after interruption. Seeds insert reference rows only when absent. Existing role permission edits, country-region changes, labels, company fields, and identities are not overwritten. Seeds never create applicants/admins/customers/contacts or assign roles to people. Countries are all 249 ISO 3166-1 entries generated from pycountry 26.2.16 into a committed package-free JSON dataset. Caribbean defaults to Central America; Mexico defaults to Central America as a configurable business choice. Turkey and Egypt are countries mapped to MENA. Countries outside these territories map to Other; business regions are not geopolitical assertions.

Required runtime environment: `DATABASE_URL`. Remote database connections validate TLS certificates. Never put database credentials in frontend/public configuration.

Required live mail environment: `RESEND_API_KEY`, `EMAIL_FROM` (verified sender), `APP_PUBLIC_URL` (HTTPS public application origin). Until all three are present, config is false and registration/resend/forgot/reset fail closed with a public setup notice. No developer authentication bypass or seeded administrator exists. The test-only mail transport cannot be set or used in production. Verification/reset tokens appear only in mail, never API responses or logs. Mail-delivery failure preserves a generic public response and invalidates the undelivered token; the user can resend. Live delivery must be tested separately after provider setup.

## Security/data relationships

`crm_users` is the immutable UUID business identity. `crm_auth_credentials` stores salted Node scrypt hashes (N=32768,r=8,p=1,64-byte key). `crm_auth_sessions` stores SHA-256 hashes of 256-bit random session secrets and a CSRF hash; the CSRF token is deterministically HMAC-derived from the private random session cookie, allowing safe recovery via `/me` without plaintext storage. `crm_auth_tokens` stores hashed single-use VERIFY (24h) and RESET (30m) tokens. Both initial ownership verification and password reset revoke all sessions. Auth limits are persistent 15-minute SQL buckets, hashed by operation + IP/account. Browser auth POSTs are restricted by JSON and same-origin checks; business mutations require the session-bound CSRF token.

New applicants are UNVERIFIED with only a row in `crm_role_requests`, never assigned roles. Initial verification accepts only an unverified ownership marker and UNVERIFIED/PENDING_APPROVAL status. In one transaction it installs a freshly salted scrypt hash of the mailed form's password, deletes **all** sessions for that UUID, consumes all VERIFY tokens, and only then records the first email verification and transitions ordinary applicants to PENDING_APPROVAL. Only confirmed ownership of the five exact allowlisted emails bootstraps the initial Admin role and ACTIVE status. This closes account preregistration: an attacker's signup password and preverification sessions cannot become the owner's active administrator credentials, even when the owner's duplicate registration was ignored. Already-verified users cannot use verification to change their password; they must use mailed password recovery. REJECTED/SUSPENDED users cannot verify or reactivate through a stale link. The recorded bootstrap-completed flag and single-use verification prevent later re-elevation after suspension/demotion. No domain-based grant, token-only compatibility path, authentication bypass or production test injection exists. Approval never sets email verification. Suspended/rejected/unverified/pending sessions receive no business data.

Verification first looks up a candidate VERIFY token without locking, then locks the credential before `crm_security_guard`, followed by the user and the freshly revalidated token. Candidate lookup alone never authorizes any write; expiry, purpose and candidate UUID are checked again under the token lock, and verification/status checks use the locked user row. Credential-first ordering matches login/reset and prevents login from issuing a session with the replaced preregistration hash after verification commits. User-before-token ordering deliberately matches `issueMail` (user then tokens), avoiding a resend/verification deadlock; locking the token before the user would invert that existing order. Credential replacement, session/token deletion, ownership marker, status, Admin assignment and audit either all commit or all roll back.

Users connect many-to-many to active roles via `crm_user_roles`; roles connect to permissions via `crm_role_permissions`. `crm_security_guard` row 1 serializes all user administration, role permission edits, country mapping updates, and verified allowlist bootstrap. Admin changes recheck the actor within the transaction, audit before commit, and roll back if no effective active top-level administrator remains. Core protected roles retain all thirteen V1 permissions. Every contact create/update/delete locks its customer parent first and clears any existing primary before making another primary, guaranteeing zero or one primary under concurrency through the API. Direct SQL writers must preserve that invariant.

`crm_countries` + `crm_business_regions` + `crm_country_regions` provide editable mapping. Customers store country; region is joined dynamically, so mapping updates immediately affect customer DTOs and filters without stale copies. Company is blank singleton row 1, neutral UTC/USD defaults only. Customers reference creators/updaters; contacts reference customer and actors; safe audit events record actions, entity IDs, changed field names, statuses and role codes, never credentials or private mail tokens.

## Verification and limitations

Verified 5 November 2026: migrations and seeds each applied twice successfully in the original backend checks. After the account-prehijack fix, `pnpm check` passed and `pnpm exec vitest run tests/backend*.test.ts` passed **28 tests**: 11 isolated credential/policy/validation tests and 17 managed-TiDB integration tests. The full integration suite uses the real Express Router and real SQL, a private nonproduction mail transport, one outer transaction and real per-route savepoints; the outer transaction is rolled back even after failure. TiDB savepoint compatibility was separately verified. Fixtures refuse to overwrite any of the five existing allowlisted identities; once real admins exist, run against an isolated database copy. The new regression cases have their own nested rollback savepoints so their temporary Admin accounts do not affect other last-admin assertions. Tests skip managed-DB integration explicitly when DATABASE_URL is absent, rather than claiming it passed.

Coverage includes the register→mailed verification→pending/allowlisted Admin flows, requested roles never granting access, multi-role permission union, immediate suspension/permission revocation, direct API denial, secure opaque cookie/CSRF checks, Sales/Pricing/Employee/Technician restrictions, company persistence, complete customer fields, duplicate warnings, search/filter/pagination, primary-contact changes/scoped deletion/parent locking, archive/restore, all 249 countries/seven regions/dynamic mappings, protected core/self/last-effective-admin policies, safe audit, editable seed preservation, single-use verification/reset, password reset/session revocation, expiry, persistent rate limits, absence of products, and CSRF-protected logout. The test proves the parent-lock path and sequential primary invariant; it does not claim a separate simultaneous-connection concurrency stress test.

The account-prehijack regression uses `kme2medical@gmail.com`: attacker preregistration and two preverification logins, ignored owner duplicate registration with a different password, and verification with a third password chosen in the mailed form. It asserts both old sessions resolve to null and cannot read the Admin API, the attacker's and duplicate-signup passwords are rejected, the mailed-form password signs in as exactly that verified ACTIVE Admin UUID, tokens are consumed, replay cannot change the credential/verification marker, only one bootstrap audit event exists, and no secrets appear in audit. The `eadlr1@gmail.com` guard regression covers missing/short/overlong passwords, unknown fields, nonexistent/expired/wrong-purpose tokens, invalid account statuses, valid initially-unverified PENDING_APPROVAL ownership, and a stale token against an already-verified/suspended account. Combined with the two existing Admin fixtures and the policy allowlist test, all four exact allowlisted entries are covered. Lock-order assertions verify the credential→guard→user→token path; no separate simultaneous-connection race stress test is claimed.

Post-suite read-only counts confirmed **zero** CRM identities, credentials, sessions, mail tokens, rate buckets, customers, contacts and audit rows persisted. Only seeded reference data and the blank UTC/USD company remain. Live mail delivery and real browser-auth cookie acceptance remain **blocked/unverified** until provider configuration and running HTTPS Preview are available. The public forwarding probe returned 502 during this backend check, so no claim of live Preview acceptance is made.

For auth-only retention cleanup run `pnpm exec tsx scripts/cleanup-auth.ts`; it closes the pool and deletes only expired sessions/tokens and limit windows older than one day. It does not run automatically. Private logical database export is documented separately in `docs/operations.md` and implemented by `scripts/backup.ts`; do not confuse Git synchronization with database backup.

Transport security relies on HTTPS publication and a correctly configured reverse proxy. Do not enable an insecure development-cookie override in a public deployment. Proxy-derived client IP rate limits use Express's trusted `req.ip`; the parent deployment must set an accurate trust-proxy policy. Monitor Resend delivery failures operationally without logging message bodies or token URLs. This V1 does not include MFA, an external abuse-management service, authentication-provider SSO, or a durable mail job queue.
